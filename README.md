# CS-305-Software-Security
Software Security portfolio featuring the Artemis Financial Vulnerability Assessment and Practices for Secure Software projects, demonstrating vulnerability analysis, secure coding, cryptography, and software security testing.

### 1. Client and Software Requirements

Artemis Financial is a financial consulting company that provides clients with services involving savings, retirement, investments, and insurance. The company's primary concern was strengthening its existing application architecture to better protect sensitive financial information and establish a secure method of communication. My responsibility was to examine the software, identify areas of potential threat exposure, and determine which security controls needed to be implemented or improved. I considered protecting client information paramount because a single weakness could potentially compromise other aspects of the system. Establishing adequate safeguards was not only a prudent decision but also an imperative requirement for maintaining the confidentiality of financial information and the reliability of the application.

### 2. Software Security Assessment

One area I believe I performed well in was taking a meticulous approach when examining Artemis Financial's software and identifying areas that could potentially compromise its security. Rather than looking at each weakness individually, I tried to understand how the application's attack surface, input validation, and dependency inventory could contribute to broader security concerns. I also recognized the importance of risk prioritization when deciding which issues required immediate attention. Secure coding is important because a small oversight can have consequential effects on an entire application, especially when sensitive financial information is involved. I believe companies have an obligation to maintain accountability for the information entrusted to them, and implementing adequate security measures is one way to demonstrate that responsibility while protecting their operations and reputation.

### 3. Challenges and Lessons Learned

One of the more challenging parts of this assessment was determining whether the findings represented legitimate security concerns or required additional investigation. While working with OWASP Dependency-Check, I learned that interpreting scan findings requires more than simply identifying a list of reported issues. Understanding CVE identifiers, recognizing potential false positives, and examining transitive dependencies required additional research and discernment. Some findings can initially appear ambiguous, especially when the reported vulnerability does not clearly explain how it affects the application. I found this process beneficial because it taught me the importance of making substantiated decisions instead of automatically assuming every reported issue presents the same level of risk. It also reinforced that a vulnerability assessment requires patience, technical investigation, and an understanding of the application's actual environment.

### 4. Security Improvements and Mitigation Techniques

Throughout Project Two, I focused on implementing additional safeguards rather than relying on a single security measure. This included configuring TLS through HTTPS, generating a self-signed certificate using Java keytool, and incorporating a SHA-256 digest to verify data integrity. Each of these measures addressed a different security concern, which helped me understand the value of defense in depth. However, I also recognized that a self-signed certificate does not provide the same independent identity verification as one issued by a trusted Certificate Authority. My approach was deliberate because implementing security controls without understanding their limitations can create a false sense of protection. In future projects, I would evaluate the severity of identified threats, determine their relevance to the application, and select mitigation methods that provide sustainable protection without unnecessarily interfering with the software's functionality.

### 5. Functional Testing and Vulnerability Verification

After making changes to the application, I focused on verifying that the security modifications worked without interfering with its existing functionality. This involved checking the application's HTTPS endpoint, examining the TLS handshake, and reviewing the checksum output to determine whether the expected integrity value was generated. I also used dependency scanning as part of the security evaluation process. One important lesson was that functional testing and vulnerability verification serve different purposes. An application can operate correctly and still contain weaknesses that are not immediately visible. Moving forward, I would use a more systematic testing process that includes regression testing and rescanning after code changes. This would provide a more verifiable record of the application's behavior and help determine whether additional modifications introduced unintended security concerns.

### 6. Tools, Resources, and Coding Practices

Several resources throughout these projects were instrumental in helping me understand the relationship between software functionality and security requirements. OWASP Dependency-Check provided experience examining third-party components, while the official Oracle algorithm specifications helped me understand the cryptographic options available within Java. I also referenced the CVE Program when researching disclosed security weaknesses and used Maven configuration to support the application's build and dependency analysis. What I found particularly beneficial was learning how to use these resources together rather than treating each one as an independent solution. Moving forward, I intend to rely on credible documentation, established coding standards, and adaptable security practices when developing applications. I believe understanding why a tool is being used is just as important as knowing how to operate it.

I would use both Artemis Financial projects as tangible examples of my ability to evaluate software security and apply what I learned to practical development scenarios. Project One demonstrates my experience conducting security assessments, identifying potential weaknesses, and developing remediation planning recommendations. Project Two builds upon that foundation by showing how I approached security implementation, testing, and validation. Together, these projects demonstrate my understanding of the secure software development lifecycle, the importance of threat modeling, and how technical decisions influence an application's overall security posture. For future opportunities involving software engineering, cybersecurity, or government contracting, I believe these projects provide evidence of my technical development and methodical approach to solving problems. They also demonstrate my willingness to maintain an audit trail of my work, recognize areas requiring improvement, and continue becoming more proficient in secure software development.
